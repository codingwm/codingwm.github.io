How the quota library is built

  1. Collect. The same Haiku agent attempts tasks from other benchmarks (InfiAgent-DABench, DA-Code, DSBench, MLGym, MLAgentBench, RE-Bench), after a filter removes anything resembling an MLE-bench competition. Every command and output is kept.
  2. Label every failure. Each failed command, each wrong result (why the grader rejected it) and each weak-but-valid result (why it scored below the best attempt at the same task) is put into one of 22 failure categories. These labels give the target mix.
  3. Set quotas. Size 1,000; each category gets 1,000 × its share of the failures.
  4. Write rubrics until the quotas are full. For a category with room, Opus reads one of its failures and writes one rubric that would have caught it from the task and code alone, or says an existing rubric already covers it (that rubric then covers one more failure). A full category gets no more calls. A rubric counts toward the category of the failure it came from.
  5. Serve (the retrieval changed too). Each time the agent runs code, the judge gets 12 rubrics. Before: the 12 most similar to the task and code change, from the whole library, which let rubrics that read like task descriptions take almost every slot. Now: the 12 slots are first divided across categories in proportion to the failures each category's rubrics cover (e.g. 2 for code exceptions, 2 for missing packages, 2 for time limits, ...), then each category's slots go to its rubrics most similar to the task and code change. The unmatched and filtered libraries are served the old way.

Everything above uses the collection pool only; MLE-bench Lite is used only to evaluate.

How the PaperBench quota library is built

  1. Collect. The same Haiku agent attempts SUPER-Expert tasks (45 research repositories: clone at a fixed commit, set up the environment, run a reduced experiment, report JSON), after a filter removes anything tied to PaperBench's papers or their code. 257 attempts, 2,774 failed commands.
  2. Label every failure. Sonnet 5.5 puts each failed command into one of 22 categories found in this pool (missing attributes, library API changes, environment or hardware limits, missing files, ...). These give the target mix.
  3. Set quotas, write rubrics, serve exactly as for MLE-bench (see that tab): size 1,000, one quota per category, Opus writes rubrics from each category's own failures until it is full, and the judge's 12 are split across categories.

The harness is the one the earlier PaperBench runs used: the judge also sees the sandbox's files and packages, a clean verdict runs the command for real, and on submit reproduce.sh runs (capped) before the submission is accepted.

Why the floor matches the ceiling on PaperBench

PaperBench scores the final state of a paper reproduction: after the agent's 90 minutes, its reproduce.sh is run for real (up to 1 hour) in every arm, and a grader checks the result against the paper's rubric. Half of the rubric's weight is code development, graded by reading the code; the other half (does it run, do the results match) came out near zero for every arm, feedback or not, because nothing reproduces the paper's results in 90 minutes. So seeing execution output during the agent's time barely moves the score, while a judge reading the code against rubrics targets exactly the part that is earned.

Both benchmarks have been used to find what goes wrong, so these are development-set numbers.
