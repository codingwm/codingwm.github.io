Rubric libraries vs the errors the agent actually makes (MLE-bench)

How every MLE rubric library was built, its failure-category mix against the collection pool and MLE-bench Lite, what the judge was served, and the harness fixes on top · built 2026-09-27 14:36 · index

In one paragraph. The first library (wrong-answer rubrics) described almost none of the crashes that make up 89% of the agent's errors on MLE-bench. Mining the failures along the way fixed the mix (mismatch 91 → 4). Mining every state of a rollout gave a mostly-methodology library (77); filtering it to the pool's error mix (6) or weighting it by error frequency (38) brought it back. None of the library changes beat the failure-along-the-way library end to end. What moved performance was the harness: showing the judge the sandbox and the data, and actually running the deliverable at two checkpoints (judge alone 8-10 → 16-17 valid of 22; interpreter 18, floor 7).

1. How each rubric library was built

Every library comes from the same Haiku agent solving tasks in a collection pool, never MLE-bench. The pools are data-analysis tasks (InfiAgent-DABench, DA-Code: one CSV, a question) and Kaggle-style competitions (DSBench: train a model, write a submission). Every step of every rollout is recorded. The libraries differ in which part of the rollout the miner reads and in whether a filter runs after mining. The first five are built at mining time; the next four are filters of the all-states library; the last carries frequency into the library as a weight.

What the miner reads

Failure-along-the-way rubrics 431 rubrics mle-rubrics-operational

Pool
Old DA pool plus 84 DSBench competition rollouts: 5,481 rollouts.
What the miner reads
A regex classifier (mining/pool_failures.py) scans every command the agent ran and records each one that died operationally: timeout, out of memory, full disk, missing package, missing file, library API changed, test runner misused, dependency conflict, download failed. Plain Python exceptions from the agent's own logic are excluded. 708 such failure records. Opus reads each record (task, resource budget, the failing command, the script as it was at that moment, the output tail) and writes one rubric: the construct in the code that made the failure inevitable.
Selection
At mining time: only operational failure records are read, whether or not the rollout ended correct. Then near-duplicates dropped at cosine 0.90.
Code

All-states rubrics 4,294 rubrics mle-rubrics-clean

Pool
Fresh collection on the MATS cluster: DSBench 21 competition tasks x 8 = 168 rollouts, DA 270 tasks x 4 = 1,080 rollouts. 1,248 rollouts.
What the miner reads
One Opus call per rollout over the whole trace: every command and its output, each operational failure tagged (and whether the agent recovered), the final scripts, the submitted answer and the verdict. It writes up to 6 rubrics per rollout, each labelled operational (the code made a run die), methodology (the code ran but the answer was wrong) or causal (a failure forced a fallback that made the answer wrong). 5,232 candidate rubrics.
Selection
No selection: every rubric Opus writes is kept, then word-overlap duplicates (TF-IDF cosine 0.50) are dropped, removing 18%. Because a rollout supports several methodology rubrics but only one or two failure rubrics, the library ends up mostly methodology.

All-states rubrics, frequency-weighted 2,276 rubrics mle-rubrics-clean-v2

Pool
The same 1,248 rollouts as the all-states library (no new collection).
What the miner reads
Opus reads the full trace (up to 400k characters) and every rubric must cite the step numbers it comes from. Each rubric's weight is the number of cited steps that were errors (non-zero exit, Traceback, Killed, timed out, MemoryError). 82% of candidates cite no error step and weigh 0, including 96% of methodology rubrics. Paraphrases are merged instead of dropped (embedding cosine 0.82, greedy then cluster centroids), summing their weights: 4,638 candidate rubrics are merged into 2,276.
Selection
During mining: nothing is dropped; frequency is carried as a weight. It is used when serving (the weighted bars below), with two serving rules run end to end: (1) the 12 slots are split across rubric kinds by total weight (about 10 operational, 1 causal, 1 methodology), and within a kind rubrics rank by task similarity plus a small weight bonus; (2) only rubrics with weight above 0 are served, with slot shares proportional to weight squared, so all 12 slots go to operational rubrics.
Code
mining/mine_clean.py (second version); CWM_RETRIEVAL_STRATIFY / _WEIGHT / _SLOT_POWER / _EVIDENCE

Every rubric has the same shape whichever miner wrote it: a title, when it applies, the pattern, how a reviewer detects it from the task and the code alone (the judge never sees program output), what separates a real violation from a look-alike, and the consequence. Not shown: a library mixing the wrong-answer and failure-along-the-way rubrics (1,117 + 431), kept only as the record of why libraries are never blended, and a library mined from MLE-bench itself (a leakage diagnostic).

2. Failure categories: the agent's errors vs each library

Errors. An error is a code-running command whose reply was an error (non-zero exit or an error signature). Three error sources: the DSBench competition pool (425 errors over 168 rollouts), the DA pool (390 errors over 1,080 rollouts), and MLE-bench Lite (130 errors, the interpreter arm over 22 competitions; measured, never used to choose anything except the ceiling library).

Categories. The 21 categories were built by Sonnet from MLE-bench interpreter replies interleaved with rubrics, then frozen. Haiku sorts every error and every rubric into one of them (88% agreement with Sonnet on a 150-item check). Pool errors are sorted into the same 21, so all bars share one axis. Categories are opened from either side: most describe a coding mistake a rubric warns about, and one, Runtime/environment failure prevents execution, holds nearly every crash. So the error bars are dominated by that one category, and zooming into it takes the failure-kind breakdown in section 4.

Mismatch is the total-variation distance (TVD) between two distributions over the 21 categories: half the sum of the absolute percentage differences, i.e. the share of mass that would have to move to turn one into the other. 0 = identical, 100 = no overlap.

The judge never sees the whole shelf: each time the agent runs code, retrieval picks 12 rubrics by similarity to the task and the change, and the judge marks which apply and which are violated. Methodology rubrics resemble task text, so plain retrieval pulls them in even from a shelf that is mostly failure rubrics. Retrieved = the 12 served per verdict; flagged = the ones the judge marked violated. Both are compared with MLE-bench's errors. Earlier harness versions (judge only, none of the fixes in section 5), valid of 22: wrong-answer rubrics 7; failure-along-the-way (431) 10 / 8; scaled to 963, 7; the mixed library 5 (8 with 4 of 12 slots reserved for failure rubrics).

Reading. Matching the shelf worked: filtering or weighting takes the all-states library from far off to close on the pool side, and the version sorted in MLE-bench's categories lands close on MLE-bench too. It did not move results: even the shelf matched to MLE-bench itself does not beat the failure-along-the-way library. The served mix explains part of it: retrieval re-skews any mixed shelf toward methodology rubrics, while the failure-along-the-way library can only serve failure rubrics. The mixed libraries also make episodes about 1.5-2x longer (the judge flags methodology criteria and the agent iterates on them) without more medals. The weight that decides serving counts error steps, so methodology rubrics, which rarely cite an error, weigh 0 and are never served under the evidence-only rule: valuing them needs an outcome-based weight, the open next step.

Prerequisites in every judge arm above

  • Deliverable run once after the episode (MLE_FINAL_SCRIPT): the agent writes its pipeline to final.py and the harness runs it once after the episode (30 min cap) to produce the submission. Without it nothing produces a submission when no code runs during the episode. Its output is kept as final_run.log, which is how the fixes above were found.
  • Fixed preamble (CWM_FEEDBACK_PREAMBLE=1): the agent is told its code-running commands are not executed and what the reward and rubric lines mean. On SWE-bench this alone lifted the floor from 297 to 325.

Infrastructure fixes (made runs valid, not the method better)

  • Pods get a memory limit equal to the request: without it an over-budget script pushed a node into memory pressure and the kubelet evicted whole pods, collection runs and logs included.
  • Data on its own volume and 10 Gi of workspace: Autopilot's ephemeral-storage limit evicted pods on pip install torch.
  • The cluster client refreshes its token every 20 minutes: an expired token made 104 of 108 pool rollouts run against exec errors (discarded).
  • Preemption counting rule: a competition is re-run only if its pod was gone before the final run started; a final run killed mid-way is the agent's own script running out of memory and is kept as a real outcome.
  • PaperBench: commands to the container go base64-encoded (a quoted multi-line command lost its newlines, 64% of one arm's errors), and the reproducer image preinstalls jupyter.
