Rubric libraries vs the errors the agent actually makes (MLE-bench)

The five MLE rubric libraries, how each was built, their error mix against the collection pool and MLE-bench Lite, what the judge was given, the results, and the harness fixes · built 2026-09-27 15:41 · index

In one paragraph. The original library, written from wrong final answers, has no rubric about the crashes that are 89% of the agent's errors on MLE-bench (difference 91 of 100). Writing rubrics from whole rollouts covers them but mostly writes about wrong results (77). On the original 21 categories, subsampling it to the collection pool's error mix looked almost perfect (6) and the oracle exact (0). With the runtime category split into failure types they are 44 and 42 away (weighted: 49): the time limit is 55% of MLE-bench's errors but only 28% of the DSBench rollouts' and 2% of the InfiAgent-DABench + DA-Code ones', and the libraries' runtime rubrics are mostly about exceptions in the code's own logic. So the matching was never as close as it looked, which fits the three scoring within run-to-run noise of each other end to end (12-18 valid of 22).

0. The collection pool

Rubrics are never written from MLE-bench. The same Haiku agent solves tasks from other public benchmarks, every command and output is recorded, and Opus writes rubrics from those recordings. One attempt by the agent at one task is a rollout. Before any task is downloaded or used, a filter removes every task that is an MLE-bench competition or shares its distinctive name words (all 75 MLE-bench competitions plus the dev one, so all 22 of MLE-bench Lite; rubrics_gym/holdouts/mle-bench.yaml).

1. Rubrics from wrong final answers (the original) 1,076 rubrics mle-rubrics-onpolicy-all

How it was built
First collection, InfiAgent-DABench + DA-Code only (5,397 rollouts of one-CSV questions). For every rollout whose final answer was graded wrong, Opus reads the task, the final scripts, the answer and the grader's verdict, and writes one rubric: what a reviewer could have checked in the scripts to catch it. It never sees the commands the agent ran or their errors, so it cannot write about crashes.
What is kept
Only wrong final answers are read. A rubric is dropped when its title and applies-when line are at least 0.90 cosine-similar (text embeddings) to one already kept. No matching to any error distribution.
Code
mining/run_da_pool.py -> mining/mine_mle.py (wrong-answer prompt)

2. Rubrics from whole rollouts, no matching 4,294 rubrics mle-rubrics-clean

How it was built
Third collection: 1,248 rollouts, 168 DSBench (21 tasks x 8) and 1,080 InfiAgent-DABench + DA-Code (270 tasks x 4). One Opus call per rollout with the whole trace: every command and its output, each crash marked (and whether the agent recovered), the final scripts, the submitted answer and the grader's verdict. Opus writes up to 6 rubrics per rollout, each tagged as a crash rubric (a code pattern that made a run die), a wrong-result rubric (the code ran but the answer was wrong) or a crash-caused wrong-result rubric (a crash forced a fallback that made the answer wrong). 5,232 candidate rubrics.
What is kept
Everything Opus writes is kept except word-overlap duplicates (TF-IDF cosine 0.50), which removed 18%. No matching. A rollout supports several wrong-result rubrics but only one or two crash rubrics, so the library ends up 68% wrong-result rubrics while most of the agent's errors are crashes. This is the parent of the next three.
Code
scripts/archive/mle_clean.sh -> mining/mine_clean.py (first version)

3. Whole-rollout rubrics, subsampled to the collection pool's error mix 615 rubrics mle-rubrics-clean-m2

How it was built
A subset of library 2; nothing new is written. Target: the errors of the 168 DSBench rollouts in the same collection (425 errors), the part of the pool shaped like MLE-bench. Those errors and all 4,294 rubrics are sorted into MLE-bench's 21 categories (it uses the category names, not how often each occurs on MLE-bench). Each category gets a number of rubrics proportional to its share of the DSBench errors, 620 in total, filled with that category's rubrics in the order they were written and capped by how many exist.
What is kept
A subsample after writing. Chosen over alternatives by how well a subsample built on half of the DSBench tasks matched the other half, never by MLE-bench. (A first version sorted into categories built on our own rollouts instead; it matched MLE-bench much worse, 30 vs 6, because the two category systems disagree.)
Code
analysis/curation_eval.py

4. Whole-rollout rubrics, weighted by errors explained 2,276 rubrics mle-rubrics-clean-v2

How it was built
Same 1,248 rollouts, mined again. Opus reads the full trace (up to 400k characters) and every rubric must cite the step numbers it comes from. A rubric's weight is how many of its cited steps were errors (non-zero exit, Traceback, Killed, timed out, MemoryError). 82% of candidates cite no error step and weigh 0, including 96% of wrong-result rubrics. Rubrics that say the same thing are merged instead of dropped (0.82 cosine, then again between merged groups) and their weights added: 4,638 candidates become 2,276 rubrics.
What is kept
Nothing is dropped; how often each problem happened is kept as the weight and used when choosing which 12 rubrics the judge gets. Two ways of choosing were run: (a) the 12 are split between the three kinds in proportion to each kind's total weight (about 10 crash, 1 crash-caused, 1 wrong-result), most similar to the task first with a small bonus for weight; (b) only rubrics with weight above 0 can be chosen, split in proportion to weight squared, so all 12 are crash rubrics. The purple bars count each rubric by its weight.
Code
mining/mine_clean.py (second version); CWM_RETRIEVAL_STRATIFY / _WEIGHT / _SLOT_POWER / _EVIDENCE

5. Oracle: whole-rollout rubrics, subsampled to MLE-bench's own error mix 621 rubrics mle-rubrics-clean-oracledist

How it was built
The same subsampling as library 3 (621 rubrics), but the target is MLE-bench Lite's own errors from the real-execution run. It uses the test set, so it is not a method: it answers whether a library whose mix matched the test errors exactly would score better.
What is kept
A subsample after writing, targeted at the test set. It matches exactly on the 21 categories; the split of the runtime category below shows how far it still is inside that category.
Code
mining/curate_quota.py CUR_SHARES_DIR=CUR_LABEL_DIR=data/taxonomy/perbench/mlebench

Every rubric has the same shape: a title, when it applies, the pattern, how a reviewer detects it from the task and the code alone (the judge never sees program output), what separates a real violation from something that only looks like one, and the consequence.

2. Error categories: the agent's errors vs each library

Errors. A code-running command whose output was an error (non-zero exit, or an error word such as Traceback, Killed, timed out). Three sources: the DSBench rollouts of the third collection (425 errors, 168 rollouts), its InfiAgent-DABench + DA-Code rollouts (390 errors, 1,080 rollouts), and MLE-bench Lite (130 errors from the run where every command executes, 22 competitions; only measured, and used to choose nothing except the oracle).

Categories. MLE-bench's 21 error categories (built once by Sonnet from MLE-bench's real-execution outputs and the wrong-answer rubrics, then frozen; Haiku sorts every error and rubric into one). One of them, Runtime/environment failure prevents execution, held 89% of MLE-bench's errors, too coarse to compare anything, so it is split here into failure types (red labels): an error gets its type from the same fixed regular expressions the crash rubrics are built on (exit code and output, no model), and a rubric in that category gets one from Haiku reading it against the same type definitions (analysis/split_runtime.py, 829 rubrics). Inside it MLE-bench's errors are 55% time limits, 15% exceptions in the code's own logic, 9% missing packages and 6% library API changes (% of all errors).

Difference between two distributions (total variation distance): half the sum of the absolute percentage differences over the categories, the share that would have to move to turn one into the other. 0 = identical, 100 = no overlap. Shown on the split categories; the summary also gives it on the original 21, which is what the subsampled libraries were matched on.

3. Which rubrics the judge was given, and the results

The judge never sees the whole library. Each time the agent runs code, the 12 rubrics most similar to the task and the code change are looked up (text embeddings; for the weighted library, the two ways described in its card), and the judge decides which apply and which are violated. Reading. Matching the library's mix worked on paper: subsampling or weighting takes the whole-rollout library from far off to close to the collection pool's errors, and the subsample lands close to MLE-bench's errors too. It did not improve results: the matched, weighted and oracle libraries all score within the difference between two identical runs of each other. Part of the reason is the lookup: from any library that still holds wrong-result rubrics it keeps giving the judge those, so what the judge sees drifts from the library's mix. The weight counts error steps, so wrong-result rubrics, which rarely cite an error, weigh 0; valuing them needs a weight based on whether the answer was right, the open next step.

Two basics in every judge configuration

  • The submission script runs once after the episode (MLE_FINAL_SCRIPT): the agent writes its pipeline to final.py and the harness runs it once after the episode (30 min cap) to produce the submission; its output is saved as final_run.log, which is how the fixes above were found.
  • A fixed explanation at the top of each judge reply (CWM_FEEDBACK_PREAMBLE=1): the agent is told its code-running commands are not executed and what the reward and rubric lines mean.

PaperBench with the final harness: 0.230 mean score, against 0.194 with real execution and 0.198 with no feedback (paired difference vs no feedback +0.033, 95% CI [-0.001, +0.072]). MLE-bench Lite and PaperBench have both been used to find these failures, so every number on this page is a development-set number.
