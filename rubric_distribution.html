Rubric libraries vs the errors the agent actually makes (MLE-bench)

Which benchmarks the rubrics come from, how every MLE rubric library was built, its error mix against our rollouts and MLE-bench Lite, which rubrics the judge was given, and the harness fixes · built 2026-09-27 14:39 · index

In one paragraph. The first library, written from wrong final answers, described almost none of the crashes that make up 89% of the agent's errors on MLE-bench. Writing rubrics from crashed commands fixed the mix (difference 91 → 4 of 100). Writing them from whole rollouts gave a library that is mostly about wrong results (77); subsampling it to DSBench's error mix (6) or weighting it by errors explained (38) brought it back. No library change beat the crash-rubric library end to end. What improved results was the harness: showing the judge the sandbox and the data, and really running the submission at two points (judge alone 8-10 → 16-17 valid of 22; every command running 18; no feedback 7).

0. The collection pool: which benchmarks the rubrics come from

Rubrics are never written from MLE-bench. The same Haiku agent solves tasks from other public benchmarks, every command and output is recorded, and Opus writes rubrics from those recordings. One attempt by the agent at one task is a rollout. Before any task is used, a filter removes every task that is an MLE-bench competition or shares its distinctive name words (rubrics_gym/holdouts/mle-bench.yaml).

What Opus reads
For every rollout whose final answer was graded wrong, Opus reads the task, the final scripts, the answer and the grader's verdict, and writes one rubric: what a reviewer could have checked in the scripts to catch it. It never sees the commands the agent ran along the way or their errors.
What is kept
Only wrong final answers are read. Near-duplicates are then removed: a rubric is dropped when its title and applies-when line are at least 0.90 cosine-similar (text embeddings) to one already kept.

From crashed commands 431 rubrics mle-rubrics-operational

Rollouts used
First collection: 5,397 InfiAgent-DABench + DA-Code rollouts and 84 DSBench rollouts, 5,481 in total.
What Opus reads
A fixed set of regular expressions (mining/pool_failures.py) checks every command the agent ran and records each one that died for an environment reason: time limit, out of memory, disk full, missing package, missing file, library API changed, test runner misused, dependency conflict, download failed. Plain exceptions in the agent's own logic are not included. That gives 708 crash records. For each record Opus reads the task, the time and memory limits, the failing command, the script as it was at that moment and the end of the output, and writes one rubric describing the code pattern that made the crash inevitable.
What is kept
Only crash records are read, including crashes the agent later recovered from and rollouts that ended correct. Near-duplicates removed at 0.90 cosine.

From whole rollouts 4,294 rubrics mle-rubrics-clean

Rollouts used
Third collection: 1,248 rollouts (168 DSBench, 1,080 InfiAgent-DABench + DA-Code).
What Opus reads
One Opus call per rollout with the whole trace: every command and its output, each crash marked (and whether the agent recovered), the final scripts, the submitted answer and the grader's verdict. Opus writes up to 6 rubrics per rollout, each tagged as one of three kinds: a crash rubric (a code pattern that made a run die), a wrong-result rubric (the code ran but the answer was wrong), or a crash-caused wrong-result rubric (a crash forced a fallback that made the answer wrong). 5,232 candidate rubrics.
What is kept
Everything Opus writes is kept, except near-duplicates by word overlap (TF-IDF cosine 0.50), which removed 18%. A rollout supports several wrong-result rubrics but only one or two crash rubrics, so the library ends up 68% wrong-result rubrics while most of the agent's errors are crashes.

From whole rollouts, weighted by errors explained 2,276 rubrics mle-rubrics-clean-v2

Rollouts used
The same 1,248 rollouts as the whole-rollout library.
What Opus reads
Opus reads the full trace (up to 400k characters) and every rubric must cite the step numbers it comes from. A rubric's weight is how many of its cited steps were errors (non-zero exit, Traceback, Killed, timed out, MemoryError). 82% of candidates cite no error step and weigh 0, including 96% of wrong-result rubrics. Rubrics that say the same thing are merged instead of dropped (0.82 cosine, then again between merged groups) and their weights added: 4,638 candidate rubrics are merged into 2,276.
What is kept
Nothing is dropped; how often each problem happened is kept as the weight, and the weight is used when choosing which rubrics the judge gets. Two ways of choosing were run: (1) the judge's 12 rubrics are split between the three kinds in proportion to each kind's total weight (about 10 crash, 1 crash-caused, 1 wrong-result), most similar to the task first with a small bonus for weight; (2) only rubrics with weight above 0 can be chosen, with the split proportional to weight squared, so all 12 are crash rubrics.

2. Error categories: the agent's errors vs each library

Errors. An error is a code-running command whose output was an error: non-zero exit, or an error word such as Traceback, Killed or timed out. Three sources: the DSBench rollouts of the third collection (425 errors over 168 rollouts), the InfiAgent-DABench + DA-Code rollouts of the third collection (390 errors over 1,080 rollouts), and MLE-bench Lite (130 errors from the run where every command really executes, 22 competitions; only measured, and used to choose nothing except the test-set subsample).

Categories. 21 error categories, built once by Sonnet from MLE-bench's real-execution outputs and the wrong-answer rubrics, then frozen. Haiku sorts every error and every rubric into one of them (it agreed with Sonnet on 88% of a 150-item check). Errors from our own rollouts are sorted into the same 21, so every bar shares one axis. One category, Runtime/environment failure prevents execution, holds nearly every crash, so the error bars are dominated by it; section 4 breaks it down.

Difference between two distributions (total variation distance): half the sum of the absolute percentage differences over the 21 categories, i.e. the share that would have to move to turn one into the other. 0 = identical, 100 = no overlap.

3. Which rubrics the judge was given, and what each library scored

The judge never sees the whole library. Each time the agent runs code, the 12 rubrics most similar to the task and the code change are looked up (text embeddings), and the judge decides which apply and which are violated. Wrong-result rubrics read like task descriptions, so this lookup picks them often even from a library that is mostly crash rubrics. Below: the library, the 12 rubrics the judge was given per call, and the rubrics the judge said were violated, each against MLE-bench's errors. Every run here uses the same final harness (section 5); only the library and the way the 12 are chosen differ. Each configuration was run twice with identical settings (run 1, run 2).

Reading. Matching the library's mix worked: subsampling or weighting takes the whole-rollout library from far off to close to our own rollouts' errors, and the subsample sorted in MLE-bench's categories lands close to MLE-bench's errors too. It did not improve results: even the subsample matched to MLE-bench's own errors does not beat the crash-rubric library. Part of the reason is the lookup: from any mixed library it keeps giving the judge wrong-result rubrics, while the crash-rubric library can only give crash rubrics. The mixed libraries also make episodes about 1.5-2x longer (the judge flags wrong-result rubrics and the agent keeps revising) without more medals. The weight counts error steps, so wrong-result rubrics, which rarely cite an error, weigh 0 and are never chosen when only weight > 0 is allowed; valuing them needs a weight based on whether the answer was right, which is the open next step.

Two basics in every judge configuration above

  • The submission script runs once after the episode (MLE_FINAL_SCRIPT): the agent writes its pipeline to final.py and the harness runs it once after the episode (30 min cap) to produce the submission. Without it nothing produces a submission when no code runs during the episode. Its output is saved as final_run.log, which is how the fixes above were found.
  • A fixed explanation at the top of each judge reply (CWM_FEEDBACK_PREAMBLE=1): the agent is told its code-running commands are not executed and what the reward and rubric lines mean. On SWE-bench this alone raised the no-feedback run from 297 to 325 solved.

Infrastructure fixes (made the runs valid, did not change the method)

  • Each sandbox container gets a memory limit equal to its request: without it one script over budget pushed a machine into memory pressure and Kubernetes evicted whole containers, rollouts and logs included.
  • Task data on its own disk and 10 GB of workspace: the cluster's storage limit evicted containers on pip install torch.
  • The cluster connection refreshes its login every 20 minutes: an expired login made 104 of 108 rollouts run against connection errors (discarded).
  • Counting rule: a competition is re-run only if its machine was reclaimed before the submission script started; a submission script killed mid-way ran out of memory on its own and counts as a real outcome.
  • PaperBench: commands to the container are base64-encoded (a quoted multi-line command lost its newlines, 64% of one run's errors), and the reproduction image preinstalls jupyter.

PaperBench with the final harness: 0.230 mean score, against 0.194 with real execution and 0.198 with no feedback (paired difference vs no feedback +0.033, 95% CI [-0.001, +0.072]). MLE-bench Lite and PaperBench have both been used to find these failures, so every number on this page is a development-set number.
