Rubric-grounded code world models — evaluation roadmap

MLE-bench, KernelBench and SWE-bench are fully held out; rubrics are mined only from external datasets. What is measured, what is built, what is next.

1Standard evaluation practice for MLE agents

MLE-bench is the reference protocol. An agent receives a Kaggle competition's public data and description and must produce a submission.csv; that file is scored by the competition's own metric against a held-out private split, and the score is placed on the competition's real historical leaderboard. The headline number is medal rate — the share of competitions clearing the actual bronze, silver or gold thresholds, which are set as leaderboard percentiles so a medal means comparable achievement whether a competition drew 200 entrants or 5,000. Above-median rate is the usual secondary figure. Attempts run under a fixed wall-clock and hardware budget with no internet access, and because agent variance is large, results are reported over multiple seeds as pass@1 or pass@k: the strongest published setup, o1-preview with AIDE scaffolding, earns bronze or better in 16.9% of competitions at pass@1 and 34.1% at pass@8. Grading is always done by the released grader rather than a re-implementation, and a 22-competition "Lite" split exists for cheaper runs. Contamination is an acknowledged weakness, since the competitions predate current model cutoffs.

3Training (mining) datasets

Thirteen datasets, 1,176 mining units, all counts post-leakage-filter and read from the frozen pool manifests at render time. The filter removed nine exact MLE-bench competitions sitting inside DSBench and MLAgentBench, two hundred constant-perturbed KernelBench copies inside robust-kbench, and flask and sympy inside SWE-smith's own repo profiles. Everything is human-authored except SWE-smith, whose bugs are LM-injected — the one large synthetic block, and worth stating plainly since synthetic bugs need not resemble real failure modes. SWE rows count repositories rather than task instances, so they are not directly comparable to the task counts above them.

Five arms each get 1800 s on the same program, which already carries an official score, and are judged on whether they beat that score. The rubric arms clear the unguided control (0–10%) by two to three times, so the channel carries real signal, but they lose to interpreter-only, 23.0% against 38.8% pooled over 227 attempts. The interpreter never breaks a program while the world model breaks a substantial fraction, which removes its chance to score at all. Growing the library from 151 to 708 rubrics changed nothing — 33, 24, 18, 20, 25% — even though rubric quality over those same stages rose from 0.00 to 0.38 error precision and 0.00 to 0.48 recall. Quality improved and utility did not follow, which points at retrieval and actionability rather than rubric correctness.

Bars compare within a stage only. Each stage's eval set is a nested prefix, so later stages face harder competitions and roughly half the interpreter's apparent 52→31% decline is task mix rather than degradation; on the five competitions common to every stage the same arm swings ±11 points at fixed sample size. Stages 3 to 5 are incomplete (15/17, 22/24, 26/29) and the missing competitions are the hard ones. Medal rate is absent for this campaign, so this is not the published MLE-bench metric.

Throughput is set by task execution cost rather than by curation, since a rubric needs a program that actually ran — and, for the performance family, one that was graded twice. Pods scale linearly at one competition each, so 1,000 rubrics is about 220 pod-hours at the production rate, roughly seven hours across thirty pods, and materially less on the lighter external datasets that dominate the mining pool.

6Next: 1,000 rubrics uniformly across the mining poolnot started

Curate 1,000 rubrics distributed uniformly over all thirteen mining datasets and evaluate, producing a scaling-law figure with rubric count on the x-axis and end-to-end accuracy on the y-axis, plus companion panels for error and performance precision and recall. Two things this run has to do that the current experiment cannot: hold the eval set fixed across rubric counts, since the present design varies library size and task difficulty together and so has no real scaling axis; and capture medal rate and above-median, which the harness computes but which were missing from the stage campaign because the medal fields postdate that code snapshot and the per-attempt rows were dropped by an artifact-glob bug. Both are fixed, so a rerun yields the metric comparable to published MLE-bench numbers.

7Next: collect on the held-out-safe pools, then re-run e2enot started

Collection now runs end to end on the external domains, verified on DSBench (five and four performance rubrics on two tasks) and on kernels (six), with error rubrics in both. The sequence is to mine across DA-Code, DSBench, InfiAgent-DABench, TritonBench, reference-kernels, BackendBench and the SWE pools into rubric_db_mle, rubric_db_kernel and rubric_db_swe; audit each database with build_domain_db.py, which traces every rubric to its source task and fails the build on a held-out origin; then evaluate on the fully held-out benchmarks, giving leaderboard-honest numbers for the first time. Two gaps to settle first are measurement decisions rather than plumbing: kernel and SWE failures surface inside the grader rather than the interpreter, so error-rubric yield in those domains is currently limited to script-level defects, and SWE error truth needs extending from exception class to failing-test identity.
