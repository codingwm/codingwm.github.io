Interpreter vs coding world model vs both together (run of 2026-09-14)

SWE-bench Verified (500) and MLE-bench Lite (22) · every arm, its plots, and click-to-expand case studies with the complete trace · built 2026-09-15 10:58

Setup. Same Haiku 4.5 agent, prompt loop and limits in every arm; only the environment differs. Interpreter: every command runs in the sandbox (SWE 60 s cap per command, MLE 600 s). Floor: commands the router classes as code execution never run and return a notice. CWM only: those commands never run; the judge (Opus 5 or Haiku 4.5) grades the current git diff against the 12 rubrics retrieved for the task (mined 1000 for SWE, on-policy library for MLE) plus the standing task criterion, and the agent receives the predicted reward and every applicable rubric's text with its own [reward 0|1], behind a fixed preamble. Dual N s: the routed command runs for real and is killed at N seconds; the agent gets its real output (or the partial output and a "killed" line) and the verdict. In this run the agent's instructions state which of these channels it is on; package installs always run; judge calls time out at 120 s; every judge call is timed. MLE arms all write final.py, run once uncapped at collection, then graded by the official mlebench grader. SWE-bench Verified: all 500 instances, official FAIL_TO_PASS / PASS_TO_PASS grading; interpreter run-to-run noise is about 8 instances. Plan and code: docs/PLAN_H2_0914.md, run_arm.py, run_mle_arm.py.
Conclusions. 1. Telling the agent that its runs do not execute lifts the floor from 297 to 325; the CWM-only arm then adds nothing over the floor (Opus 324, Haiku 307): the agent issues a median of 2 graded commands per instance. 2. The dual arms match the interpreter (Opus 346-352, Haiku 339-342 vs 347) because on SWE-bench the budget almost never binds (0.1-0.3% of routed commands killed): a dual arm is the interpreter plus a verdict, costing 1.4-2.1 extra minutes per solved instance and, with Opus, about 12x the money. 3. Opus is the better judge by 6-17 instances at about 7x Haiku's cost; neither turns a verdict into solve rate the interpreter does not already have. 4. On MLE-bench the one uncapped final.py run at collection puts the floor at the interpreter's level (2 medals each); the CWM-only arms leave only 7 (Opus) and 3 (Haiku) valid submissions of 22 because a pipeline never run during the session usually fails at collection; the dual arms (budgets binding on 13-26% of commands) leave 19-20 valid, 1-2 medals, like the interpreter. 5. No arm is faster or cheaper than the interpreter on the instances both solve. 6. The rubric libraries describe a different distribution of failures from the one the agent meets at test time (20 categories derived from the data; mismatch 73 of 100 on SWE-bench, 98 of 100 on MLE-bench; last tab).
Why there is no efficiency gain on SWE-bench, and where the loss comes from. The most an execution-free method can save is the time the interpreter spends executing. On SWE-bench that is 0.71 min of a 4.4 min solved instance (16%): 21 execution commands at about 2 s each. The world model is not cheaper than what it replaces. Never running code (CWM only, Opus) does save time: 3.8 min against the interpreter's 4.4 on the instances both solve, a 14% saving, but it costs 23 solves (324 vs 347) and $1.46 against $0.20. Running and grading (dual) cannot save anything by construction: the command still executes and the judge is added in series. In the 60 s arm the judge costs 1.46 min against the 0.39 min of execution it accompanies, 3.7x, so wall clock goes 4.4 → 4.9 for the same solve rate. Iteration is the second effect, and it shows on the failures. On instances the arm solves, the world-model arms issue slightly fewer commands than the interpreter (56 vs 53 for CWM only, 56 for dual). On instances they fail, they issue clearly more: 88 commands and 8.0 min for CWM only against the interpreter's 72 and 6.8. Without a real error message the agent keeps editing and re-grading, which is where the extra wall clock and cost go. MLE-bench is the mirror image: execution is 44.4 min of the interpreter's wall clock, so skipping it cuts the median competition from 44.8 to 16.9 min, a 2.6x saving, but only 7 of 22 runs then leave a valid submission, because a pipeline that never ran during the session usually fails when it is finally executed.

Why the efficiency story differs between the two benchmarks

Where a task's wall clock goes, per benchmark (median minutes)

Running code is 0.8 of 4.8 min on SWE-bench (16%) and 38 of 45 min on MLE-bench (86%). That share is the ceiling on what any execution-free method can save. On SWE-bench the world model costs more than the execution it removes; on MLE-bench it removes far more than it costs, but what it removes is the training that produces the deliverable.

The question. Our rubric libraries were mined from agent failures on separate collection pools. Do they describe the same kinds of failure the agent actually runs into when it works on the benchmarks? What is being compared. On one side, the feedback the agent received in the interpreter run of this sweep, the arm where every command really executes: each time the agent ran code (a script, a test command), the sandbox's reply was recorded. That is 12,840 replies on SWE-bench (3,126 of them carrying an error) and 606 on MLE-bench (130). On the other side, all 1,000 rubrics of the SWE library and 1,076 of the MLE library. How the categories were made. Not written by hand. Claude Opus 5 was shown 48 random samples of 50 items each, mixing error replies, successful replies and rubrics from both benchmarks, and asked to name the kinds of failure or outcome it saw in each sample; that produced 681 candidate categories. A final call merged those candidates into exactly 20 mutually exclusive categories with a definition and examples for each, required to cover both sides. How each item was filed. Claude Haiku 4.5 read every single item and assigned one category: a sandbox reply by the root signal in it (the exception that was raised, the assertion that failed, or the run finishing cleanly), and a rubric by the symptom a patch violating it would produce when run. Reading the charts. Two bars per category: how often it appears at test time (share of the error replies the agent received) and how often it appears in the library (share of the rubrics). The single mismatch number is the total variation distance between the two distributions, in percentage points: 0 means identical, 100 means disjoint. Code: analysis/taxonomy_induce.py; data: data/taxonomy/induced_h2/.
